## RTW 服务端 key registry 与签名回执接缝

`--mode evaluate-rtw` 是**显式、默认关闭**的离线 Worker 读面，要求配置 RTW base URL 与私有 Worker token 文件；这个模式拒绝同时传本地 `--review/--trust`。BTW 先按原来源文件冻结 case，再从 RTW Worker 私有 `GET /internal/v1/knowledge/answer-grounding/reviews/:case_sha256` 读取 RTW PG/Outbox 不可变 review receipt，随后独立 `GET /internal/v1/knowledge/search-citations/:search_id` 复核耐久引用，最后以 `GET /internal/v1/knowledge/reviewer-keys/:key_id` 读取**当前** registry 状态。回执原字节 `case_json` 必须与本地 case 完全相等，review JSON/SHA、SearchID/AnswerID、RTW accepted answer SHA、citation pack ref/hash、reviewer/key/revision/签名逐项比对；RTW 的 `trace_authority_status=external_case_unverified` 必须保留。本地原始 RTW 结构化日志和 DC 用量/模型响应仍由 `freeze` 独立核，不把 RTW PG 回执提升为 OTLP/Collector 证明。Worker 响应数据合同见 [review receipt Schema](/Users/edy/Sea/.codex-worktrees/sea-btw-grounding-rtw-registry-20260915/contracts/jsonschema/search-answer-grounding-rtw-review-receipt.v1.schema.json) 与 [key registry Schema](/Users/edy/Sea/.codex-worktrees/sea-btw-grounding-rtw-registry-20260915/contracts/jsonschema/search-answer-grounding-rtw-reviewer-key.v1.schema.json)。

实际 `evaluate-rtw` 参数还**强制**提供与 `freeze` 相同的 `--usage-report/--rtw-report/--rtw-trace-log` 三份原字节并重新冻结，要求所得 case 与输入 `case.json` 逐字相等、SHA-256 相同，之后才调用 RTW Worker；防止调用者在本地替换 RTW 不掌握的 trace/模型字段。`citation_pack_ref` 是 RTW 的 `durable_ref=search-citations/sha256/SHA256(search_id bytes)`；`citation_pack_sha256` 是固定 EvidencePack JSON 原字节的 SHA-256。两者是独立身份，消费者逐项核对并拒绝把 durable ref 后缀冒充 pack hash。

已注册测试 key 为 `active` 且签名/来源均有效时，**仅合成** label 可得到 `synthetic_rejected_unsupported` 等离线演练结果；当前 registry 一旦 `revoked`，即使历史签名在审阅时有效也降为 `pending_revoked_authority`，不删除原审阅事实。review 回执 404 保持 `pending_human_review`，当前 key 404 保持 `pending_authority_registry`。因为当前 CLI 的 RTW URL 本身仍由调用方指定，选一个伪 Worker 也可能返回自签 `human_admin` key；这一路**仍只给 `pending_authority_service_identity`**，不会成为真人支持/拒绝。未来需要平台独立固定 RTW 服务身份与可信路由、真实管理员审核和撤销治理，才能提升 `human_admin`。所有成功产出的决策保持 `activation=none,runtime_blocking=false`，不修改用户侧答案或误报在线语义质量。
