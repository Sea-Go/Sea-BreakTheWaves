# 正式搜索 API 的原生三路物理后端交接

当前 BTW 独立叶子从搜索开发远端 `8edaca88e60a84d5ea0e3566de475a8d1a072944` 开始。写区 `[W1]` 为本叶子 `cmd/api` 的配置、物理装配与验收入口，以及 test-only 的 `internal/transport/http/search` 交接和 Scope 取消分类；只读区 `[R1]` 为三 lane、内容 Build、RTW/DC 当前开发树与 Sea-Docs。依赖 `[D1]` 是根 `go.mod` 已解析的 Milvus Go SDK `v2.6.2`、tRPC-Agent-Go 核心 `v1.8.1` 与锁定 Milvus Lite wheel；生成物 `[G1]` 不手改；外部 `[X1]` 仅待任务自建的本机 RTW/DC/PG/Lite/对象目录，生产和用户已有实例均不写；范围外 `[N1]` 为 BTW/RTW/DC 开发集成树、Docs 与其他脏工作树；临时 `[T1]` 为验收一次性目录。主职责 `[C6]` 物理配置/SDK 装配，跨 `[C2]` 搜索、`[C7]` RTW发布ABI、`[C5]` 现有原生Graph/Runner、`[C8]` 验收。

`BTW_SEARCH_MODE` 必须显式选 `native-hybrid` 或 `native-milvus`，另给 `BTW_SEARCH_MILVUS_ADDRESS` 与一份直接可读的 `BTW_SEARCH_NATIVE_FILE`。该 JSON 严格是 `sea.search.native-backends.v2` 的六个字面字段：`schema_version,engine,namespace,sparse_backend,dense,multivector`，其中两个HNSW对象各为 `m/ef_construction/ef_search`。`native-hybrid`只允许`engine=lite,sparse_backend=frozen_ip_postings`：Dense和token Multi-vector使用同一任务Lite 3.2.1的两个独立HNSW Collection，学习型Sparse使用已有内容寻址Shard中的真实 weighted posting lists 做IP候选TopK。`native-milvus`只允许`engine=milvus,sparse_backend=milvus_ip`，三路均用真实Milvus Standalone的独立Collection；[Milvus官方文档](https://milvus.io/docs/sparse-inverted-index.md)明确区分外部Sparse embedding的`SPARSE_INVERTED_INDEX/IP`与BM25。重复、转义别名、未知字段、模式/引擎错配及隐式exact fallback均拒启动。两个HNSW Collection digest同时包含当前IndexRef与完整物理配置；RTW v1 `IndexManifest`只签三个Lane Ref/Profile/Probe，**没有**物理namespace/HNSW或Sparse后端资格收据，故正式内容worker仍须在READY之前把物理资格冻结到同代权威清单，不能从Ref猜物理集合。

Native 模式的 RTW HMAC Scope 先照旧验证。进入 Runner 或用户 BGE 查询前，API 再从 RTW Worker 重读**当前人工激活**的 Snapshot，核签名版本、三个不同的完整 LaneIndex Ref/同 BuildID、generation、ChunkManifest、配置的模型/词表空间及有效 SourceRevision 全集；Multi 必须是 `mask=valid` 和固定 MaxSim 聚合。Hybrid只读`Load`两个Lite HNSW Collection并逐字段/index/行回核，Sparse则`Load(ref)`重读完整冻结Shard、对每个Posting与原学习权重重新计算校验；Standalone模式另将Sparse物理Collection按`SPARSE_INVERTED_INDEX/IP`校验。三个lane都以固定来源执行冷加载probe，再缓存不可变Snapshot交原`search.Service`。请求在同一tRPC Graph中分别由Dense ANN、Sparse查询词项的**实际交集Posting内积TopK**、Multi在自身全有效范围token索引产生的chunk候选后完整矩阵MaxSim组成RRF；Sparse不会因Lite先做BM25裁候选而漏真正IP高分。缺行、错Ref/空间/mask、源撤回、取消或探针失败不产用户证据或RTW引用提交；缓存最多四个已加载发布快照，新代超过上限要求显式重启，不驱逐在途旧快照。旧`local-exact`没物理设置时的启动、签名/Tools/summary、tRPC-Agent-Go原生Span与结构JSON日志仍原行为；Milvus凭据从启动错误脱敏。

错误来源先固定：本机锁定Lite 3.2.1/FAISS 1.15.0的`SPARSE_INVERTED_INDEX`源码**不按请求IP分支**，总是先用BM25/IDF/长度归一裁TopK；本机纯语义RED报告`/private/tmp/sea-native-lite-bm25-abi-20260916.0Ze8XK/red-report.json`原字节SHA=`ff1eea829a8184a61b122188281c653a8a3efb9cda096a3a5468826c03cbc4be`，A的学习IP10高于B9，但Lite BM25将B排A，且报告明确`physical_service_started=false`。在最早Sparse候选接缝改用已有冻结Posting后，新`TestFrozenLearnedPostingIPKeepsTrueTopKBeforeBM25LengthTrap`实际用内容寻址Shard Build→Load→只访问query t1的两条Posting→TopK1 A10/TopK2 A10>B9，取消了对无关t2全表扫描或BM25先裁。当前Hybrid配置与发布Profile/坏lane/错代/撤回前门禁聚焦race、受影响三包race、vet/mod verify/diff通过。
