# WS07→WS08→H10 同次覆盖交接验收

本脚本从同一个父运行中启动隔离 RTW Favorite、DataCenter platform、PG16、ClickHouse/dbt 和 SeaweedFS。测试只写 `warehouse/coverage/`；WS07 Publisher、WS08 Verifier、H10 Builder 的实现与 Sea-Docs 保持原样。执行：

```sh
SEA_DC_PLATFORM_ROOT=/path/to/isolated/datacenter \
SEA_RTW_FAVORITE_ROOT=/path/to/isolated/rtw \
WAREHOUSE_FAVORITE_RUNTIME=/path/to/locked/warehouse-runtime \
warehouse/coverage/combined_acceptance.sh
```

`combined_test.go` 的**真 RTW/DC**路径：旧收藏领域操作产生 assert/retract、DC 持久给 offset 1/2；WS07 自己的 consumer 先接纳 ODS、批次证据并发布 W1 原始 S3 EventIndex/BatchEvidence/SparseIndex。WS08 以另一个 PG 数据库中的真实 tRPC-Agent-Go FactGraphRuntime/Store/Outbox 接纳同源事实，`FavoriteCoverageHTTPProof` 向真实 RTW/DC 重查后调用 `VerifyPrefix/VerifySubject`。H10 `UsermodelCoveredReader` 与 `RunnerCoveredObjects` 读取同一 S3 对象，`BuildCovered` 得到默认关闭的候选。随后撤回进入领域 PG，历史 W1 仍为建立值 1，尾部显示撤回且 `CurrentComplete=false`；W2 候选才为 0。两边 DC consumer 的 ACK 各自推进，WS08 验证本身不 ACK。

第二条路径使用**第二个真实隔离 DC/PG**，RTW 业务写入与私有权威读由明确的测试 HTTP 夹具代替，因此不能称真实 RTW 多用户业务来源。夹具给 DC 按 `[u1 assert:1,u2 assert:2,u1 retract:3]` 发布同一 producer 的冻结 EventSpec。WS07 实际发布 W1/W3 和 `[1,3]`、`[2]`、空主体三份稀疏切片；Graph 在 offset 2 尚未接纳时先把 offset 3 通过 RTW 校验后的真实 Graph/Store/Outbox 提交，验证 W1 **候选值**仍为 1、已知尾部 3 和 `CurrentComplete=false`，W3 的 `VerifyPrefix` 只能返回 Pending。补入 offset 2 并重投 offset 3 后，W3 验根成功，H10 对 u1/u2/空主体分别得到 0/1/0。旧 W1 EventIndex 与候选 hash 保留。

拒错门禁使用**同次 Publisher 产生的原字节**：省去全局 offset 2、RTW 权威主体与索引主体冲突、少领域 PG 事实、篡改 WS08 SparseIndex 输入、篡改 H10 真 S3 SparseIndex 对象，均不得变为可用候选。ClickHouse/dbt 在相同父运行里从这两条 PG ODS 导出生成独立收藏 DWD，核主体、offset 和正反状态；收藏不进入推荐曝光/成熟标签。`cross-domain/report.json` 分列真源和双主体夹具的证据等级；`cross-domain/artifacts/` 保留逐 SHA 验证的 S3 源字节与候选工件，localhost URL 仅在本次运行期间可访问。

验收止于 **WS07 发布、WS08 覆盖接纳和 H10 默认关闭候选**。没有调用 `Accept v2`、没有 FeatureSnapshot/ServingBundle 激活，也没有正式获批 FeatureSpec、真实 RTW 双用户流量、DC 用户塔或推荐效果证明。`CurrentComplete` 只表示该 PG 快照没有已知尾部；DC 全局鲜度和线上放行另有门禁。
