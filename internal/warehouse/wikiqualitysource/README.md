# Wiki 质量评阅来源 ODS

RTW Knowledge 的 `producer=ridethewind.knowledge` 与 Wiki、搜索判定、发布事件共用 DataCenter 的连续 offset。本包使用自己的 `btw-warehouse-wiki-quality` consumer 与 PG 游标，完整保留每条 DataCenter EventSpec 的 JCS、输入哈希和技术收据；非质量事件显式标记 `technical_skip`，不会计作人审 Fact。未知 `knowledge.wiki.quality.*` 版本一律拒绝。目录新事件在**默认未配置FactSet模式**时整批拒，显式v2能力只接固定`knowledge.wiki.fact-set.frozen.v1`，未知目录家族继续拒；不能跳过目录后把零散评阅冒作完整标签。

RTW 开发源 `feat/wiki-quality-human-judgment-20260916@6865022` 已固定 `knowledge.wiki.quality.judged.v1` 的九键外层 Event、三十二键单 Fact payload、原 Event 不含末尾 LF 的 SHA、RFC 8785 JCS SHA 与 Worker 私有 GET；`V1Verifier` 按该源 Golden 精确核缺漏/重复字段、版本、FactID、原引文 SHA 和自身 byte span、AI/人工修订、0–3/undetermined、来源撤回和历史重判。RTW 私有 GET 还按其不可变 Source/Wiki 对象复核当时引用。接纳时必须同时配置原字节 Authority 与正式 Verifier：先核 RTW 原 byte SHA，再核 RTW/DC 整 Event JCS 和 DC input hash，最后验 payload，才能写 `quality_verified`；缺席时整批在 PG 与 DC ACK 前拒绝。测试夹具 `syntheticVerifier` 仅证明事务行为，不能替代 RTW 真实评阅业务源。

`actor_id` 仅是当时获准的 RTW 管理员 JWT+名单 `userId` 字面值，可是字符串；它没有实时 UserCenter UID 资格。单 Fact 事件也不证明页面/SourceScope 的预期事实全集已列全，不能由 ODS 已收到几条评阅推导 D07 覆盖率或真人页面达标。正式 FactSet 清单、真实后台资格与外部来源的跨进程同父仍另签；产品主体不引入租户字段。

RTW默认关闭的完整目录源`feat/wiki-fact-catalog-20260916@95ce8fc`已经固定独立`knowledge.wiki.fact-set.frozen.v1` Event与原字节/JCS/目录payload三个SHA的静态Golden。新`ParseFactSetV1`从同一固定Golden核两份SourceRevision的完整范围JCS、每条FactID/原quote自身byte span、必覆盖与矛盾组、AI/manual及历史FactSetRevisionID；`HTTPAuthority.ReadFactSetEvent`从RTW Worker私有GET分别核三域。`facts_complete`只是管理员JWT名单对所列目录的声明，不证明所有事实真的被列出，也不等于UserCenter规范UID。已配置FactSet Authority+Verifier的v2 Consumer必须先通过旧库显式迁移/强schema只读探针，才会对同一连续offset接目录和质量行；没有配置时仍拒FactSet家族。当前目录还未在真实RTW→DC同父派发，**静态Golden、HTTP夹具及本机混合PG测试不能宣生产已启**。后续真实完整prefix还要核N条单Fact评阅来源，再给评测Dataset聚合证据。

**FactSet ODS v2 表合同（schema writer）。** Fresh `schema.sql`在已有v1/半扩展父表时于首表DDL前拒，不能借`CREATE TABLE IF NOT EXISTS`制造半升级；旧数据库需显式调用 `ApplyFactSetMigration(ctx,*pgxpool.Pool)` 或独立 `migrate-fact-set-ods.sql`，不是运行时读路径自动DDL。能力启用后只读 `CheckFactSetSchema(ctx,*pgxpool.Pool)` 在读DC/ACK前核nullable `ods_event.fact_set_payload_jcs_sha256 text`、`ods_event_status_v2_check/ods_event_evidence_v2_check`强三态、侧表类型/约束/FK/触发器，部分或弱扩展拒启动。完整v2重复迁移不动旧bytes、状态、游标或trigger OID；迁移不回填任何历史目录。

父表`ods_event`三态互斥：`technical_skip`的原Event字节、rawSHA、FactSet payloadSHA都NULL；`quality_verified`原Event字节与严格小写64位rawSHA非NULL而payloadSHA NULL；`fact_set_verified`三者均非NULL，rawSHA及payloadSHA严格小写64位。附加append-only `ods_fact_set(producer,source_offset,fact_set_id,revision_id,revision,base_revision_id,wiki_revision_id,source_scope_revision,payload_jcs,payload_jcs_sha256)` 以真实 `(producer,source_offset)` FK锁父表、对同producer RevisionID及FactSetID/seq唯一，原目录JCS bytes及SHA只写一次。侧表INSERT核父行必须是`fact_set_verified`且payloadSHA相同；父行延期约束核提交前同位置侧表已存在。任一写失败时**父表/侧表/独立游标同一PG事务回滚，DC ACK尚未发送**；PG提交后再独立ACK，ACK丢失重查旧行/原sha后只重试同批ACK。旧v1默认Consumer在未迁移数据库仍用原11列写`quality_verified/technical_skip`；新schema含FK侧表的所有PG fixture `TRUNCATE`已同批列该侧表。

ODS 游标、原始 Event 字节和所有技术位置在同一 PG 事务接纳，提交之后才 ACK DataCenter。ACK 丢失后的相同 batch 会核每条历史 EventID/hash/JCS/receipt/RTW 原字节及FactSet侧表后只重试ACK，改变过的收据或来源不能靠重放覆盖旧标签。`HTTPAuthority` 按固定Worker私有路径分别读单Fact与FactSet原Event字节/对应摘要，重定向/坏回执拒；其普通HTTP测试仍是夹具。`bash internal/warehouse/wikiqualitysource/acceptance.sh` 使用独立PG16测试事务、RTW静态Golden与拒错。RTW单Fact真实源同父仅在`SEA_RTW_REAL_WIKI_QUALITY_FIXTURE`可用时运行；**目录+N判断**真实同父需RTW任务私有`SEA_RTW_REAL_WIKI_FACT_SET_FIXTURE`与DC Holder同父进程才可运行，普通包测试SKIP该轮。生产者需在固定源码/同进程版本核源PG Event/当前范围、DC offset和ACK。默认无目录运行命令或产品页面质量激活。
