# BreakTheWaves 算法搜广推与 Agent 工作规范

BreakTheWaves 是**算法搜广推与 Agent 相结合的系统**。开发工作围绕“内容变成可检索物品，候选经过算法选择，Agent 理解需求并按证据交付，反馈推动效果改进”展开。目录、接口和存储为这些能力服务。用户当前明确指令优先；本技能用于本次功能实现，不自动启动整库重构。

## 何时使用与怎样执行

当前任务位于 BTW 仓库，或用户明确指定 BTW 的模块／文件时，按下表应用本技能，无需等待用户再次写出技能名称。工作目录在 Sea 父目录时，先将本次目标定位到 BTW；其他仓库沿各自规范，不扩大本技能作用域。

| 用户提出的任务 | 本技能怎样参与 | 应交付什么 |
| --- | --- | --- |
| 新增功能、改算法、接模型／工具或调整 API／Worker | 按完整目录确定能力所有者，结合两套框架规范完成实现、真实装配及必要配套 | 可调用的能力、必要契约／配置与行为、效果或代价验证 |
| 排错、修复、延迟／资源／效果优化 | 沿实际入口区分算法、模型、协议、状态和装配问题；按本次要求落实修复或优化 | 可复现依据、受影响位置、实际修正及针对性验证 |
| 代码评审、边界或实现核查 | 同时检查需求符合性、算法语义、解耦及框架生命周期 | 有源码位置和触发条件的发现；评审任务不自行转成改代码 |
| 当前架构解释或绘图 | 依据当前目录、调用与装配区分已接通、占位、历史和目标能力 | 可核对的说明／图；图内遵守通用概念约定 |
| 回退、目录恢复、技能／工程规范维护 | 使用对应范围规则，保留不涉及的工作；规范维护继续保留完整目录和两套框架细则 | 本次指定的恢复或文档变更及相应检查，不重做历史改造 |

实现类任务按 [能力落地细则](references/writing.md)、[解耦规范](references/decoupling.md) 与 [联合开发规范](references/framework-integration.md) 推进；涉及框架实现时实际加载 [go-zero](references/go-zero.md) 和 [tRPC-Agent-Go](references/trpc-agent-go.md) 的原始规范。输出应说明实际完成内容、验证及其边界，不能只给能力目录、注册清单或下一步计划。只读任务保持只读。

## 项目定位与算法边界

| 能力 | 解决的问题 | 开发时必须区分的目标 |
| --- | --- | --- |
| 搜索 | 根据查询和上下文找到相关物品／原文证据 | 查询相关性、候选覆盖、排序质量、出处与延迟 |
| 推荐 | 根据外部用户 Ontology、场景和物品信息选择内容 | 兴趣／场景匹配、反馈目标、覆盖与多样性；不直接沿用搜索相关性目标 |
| 广告算法 | 在明确广告需求后处理可投候选、匹配和效果预估 | 广告资格、预估目标与自然内容目标分开；候选和特征可复用，分数与决策不能混用 |
| Agent | 理解复杂意图、选择工具、取得证据、生成回答或计划 | 工具实际调用、证据充分性、引用正确性、结构化结果及调用预算 |
| 离线计算 | 内容理解、物品表示、样本、训练、索引与评测 | 数据完整性、训练与在线一致性、模型效果、更新成本与资源使用 |

“搜广推”是算法背景；当前目录已有 Search、Recommend、Async，没有独立广告服务。广告匹配／预估仅在具体任务涉及时实现，原先排除的竞价、预算与计费不因这个名称自动纳入范围，也不预先搭广告空模块。

### 本项目的三条协作链

```text
在线算法：查询／Ontology／场景 → 候选召回 → 融合与特征 → 排序／重排 → 结果列表
Agent：意图理解 → 检索与原文工具 → 证据组织 → 回答／计划 → 引用与结构化结果
离线计算：完整来源 → 内容与关系 → 物品表示／样本 → 训练与评测 → 模型／索引 → 在线消费
```

这些链路按需求组合，不要求每个请求都经过所有步骤。Agent 可以选择查询和工具、执行多轮取证；召回算子、特征计算、过滤和排序仍由所属算法模块提供。模型排序可以成为算法实现，但必须有明确输入、输出和效果验证，不能用一段提示词或改分数替代它。

### 已明确的产品边界

- 外部每次提供 Ontology、用户图画像及可选用户表示；BTW 聚焦物品侧。新能力不通过用户 ID 隐式回查专用画像库，也不附带训练用户塔。缺少或不匹配的用户表示使用真实可用路径并报告，不造假向量。
- 物品以完整文本来源为基础；书籍原文件、全文、自然结构和原文位置保留。临时计算窗口与子向量服务理解和检索，不自动成为独立推荐物品。
- 内容列表与生成交付分别实现：列表使用召回与排序；问答／计划在证据上调用模型并返回引用，不执行外部任务或日历。网站内容范围在召回前限制，不能最后才剔除书籍。
- 新核心通过输入输出及适配器与 DataCenter、网站、桌宠解耦。旧用户账本、chunk 与专用发布流程已退出当前核心，不能作为新功能依赖。

这些是功能职责约束；实现与环境验证的范围分别记录。详细背景与当前／目标的区分见 [架构语境](references/architecture-context.md)。

### 三个服务域怎样接入功能

| 业务所有者 | 公开入口 | 私有实现及接线 |
| --- | --- | --- |
| Search | `service/search/rpc/engine` | `internal/search` 提供查询、检索、搜索排序、工具和有据生成；由统一 API svc 创建 |
| Recommend | `service/recommend/rpc/engine` | `internal/recommendation` 持有场景交付、去重和推荐目标，复用注入的搜索能力 |
| Async | `service/async/rpc/content` | `internal/catalog`、`processing` 保存与加工资料并产生训练样本；训练执行归 DataCenter，API 和 Worker 使用同一公开内容能力 |

当前 HTTP 路径是 `api/btw.api → handler → logic → 领域公开入口 → 本域实现`。搜索按 fast、balanced、deep 三档调度；全文、内容图、向量检索分别由适配接入。svc 装配依赖，Worker 在 `service/async/rpc/cmd/worker` 装配自己的资源。没有 API→内部 RPC 网络中转，也没有全局隐式 runtime 初始化。目录中的 rpc 字样保留工程所有权，不表示存在对应进程。

### 容易放错的能力

| 能力 | 正确责任 |
| --- | --- |
| HTTP types 与领域 item | 前者由 goctl 生成；后者是跨域稳定值类型，转换集中在 mapping，领域不依赖 HTTP |
| 场景与公共检索 | 场景由 Search／Recommend 选择；Elasticsearch、Neo4j、Milvus 分别接受明确的全文范围、内容关系与表示预算，不认识网站／桌宠名字 |
| 业务 Agent 与 agentx | Prompt、工具集合和证据决策留领域；agentx 只封装框架技术与每轮生命周期 |
| catalog 与 database | 前者拥有业务表和事务；后者只提供通用连接，不复制物品状态 |
| processing 与 inference | 自然结构和语义物品由 Async 负责；DataCenter 管理并执行模型计算，不拥有 BTW 来源可见性 |
| 原文结构与计算窗口 | 章节和目录是原书结构；窗口及子向量是计算产物，没有固定 chunk 物品身份 |
| 临时 Session 与持久任务 | Session 服务本轮模型工具；任务表负责恢复和提交，不能用 Session 替代加工状态 |
| `.agents/skills` 与运行时 Skill | 此处是开发规范；线上没有旧字符串 Skill 分发，新增能力直接接算法和真实 Tool |

### 新增代码怎样选择目录

1. 查询理解与相关性进 Search，推荐目标与交付进 Recommend，资料与训练生产进 Async；先扩展已有能力，避免复制一套算法。
2. 只有相同语义且有真实跨域消费者的算子／适配进入 Common，不为绕过 internal 搬整个业务。领域公开工厂负责合法的进程内调用。
3. HTTP 变化只改 `api/btw.api`，使用 goctl 生成到 `service/btw/api`；实现写可编辑 handler／logic／svc，生成 routes/types 不手改。
4. 新模型同时补训练／加载／评测与版本；新 Agent 同时补工具／Prompt／Runner 及普通／流式消费者；新离线阶段接 Worker、任务与必要恢复。
5. 目录变化同步更新完整树和框架接线；不得用摘要表替代目录，也不得删除框架细则。退役实现不再写作当前能力。

## go-zero 与 tRPC-Agent-Go 协同规范

两边共同构成一次功能的实现要求。go-zero 保持本项目服务工程与外部合同，tRPC-Agent-Go 运行语义任务，搜广推算法与物品数据由所属领域负责。

| 开发内容 | go-zero 侧必须落实 | tRPC-Agent-Go 侧必须落实 |
| --- | --- | --- |
| 新输入／输出 | 从 `api/btw.api` 修改并生成到统一 API，补齐领域映射 | 用例把查询、Ontology、范围与证据送入实际 Run／Tool，框架结果回到业务合同 |
| 接口分层 | handler 接入与输出，logic 组织用例，svc 装配领域能力 | 任务 Agent／Tool／必要 Graph 放本域，共用 Runner 技术在 agentx，调用已有算法；不在 handler 写工具循环 |
| 配置与实例 | RestConf 与 settings 加所属算法配置，经入口与 svc 使用 | Model、工具集合、Prompt、Agent、Runner 集中装配；每轮参数不修改共享实例 |
| 预算与取消 | HTTP／模型期限和流式设置适配任务，Context 传到用例 | Runner→Tool→模型／存储沿同一取消链；局部调用限额与业务总预算同时成立 |
| 算法与工具 | 普通列表入口直接调用召回、特征和排序 | 模型需要访问算法时用 typed Function Tool／Knowledge 适配；不复制算法或回调自身 HTTP |
| 编排与状态 | 业务任务和数据提交仍由原领域负责 | 按需要选单 Agent、AgentTool、transfer、Chain／Parallel／Cycle 或 Graph；节点传状态增量，控制权与结果归属明确 |
| 回答／计划 | 公共 schema 定义结果、引用和不足状态 | 用真实证据生成并解析结构化输出；选择当前版本支持工具的输出方式，不误禁用取证工具 |
| 流式结果 | Runner→稳定业务事件→SSE，正确编码并处理写出错误 | 区分 Delta、完整结果、局部完成、终态错误和 Runner completion；公共成功还需业务结果成立 |
| 数据与会话 | 物品、原文、样本和任务状态由业务存储所有者管理 | Session／Memory／Graph State 不替代业务库或外部用户画像；实际后端装配与隔离可验证 |
| 资源关闭 | 服务 owner 停止新工作并管理其在途请求和依赖 | 请求只取消本次运行；应用等待其拥有的工作退出再关闭 Runner 与外部资源；不能假定 Stop／Close 跨框架包办 |
| 观测与扩展 | 沿服务中间件传请求身份、追踪和协议错误 | Callback／Extension／Plugin 在准确作用域生效；纯观测不短路节点或把失败改成成功 |
| 验收 | 验证真实入口、字段映射、普通／流式交付 | 验证实际模型／工具、证据、编排、终态及资源；算法质量与运行正确性分别证明 |

具体内容必须同时执行：

- [tRPC-Agent-Go 开发规范](references/trpc-agent-go.md)：能力选型、Model／Agent／Runner、Tool、Prompt 与结构化输出、Graph、多 Agent、事件、会话与关闭。

## 修改现有功能时的规范

首先判断本次改动影响哪项算法目标或 Agent 行为，再确定目录、数据与消费者。按下面的类别落实，不把“接口返回成功”当成算法能力完成。

| 要做的修改 | 实现与接入位置 | 必须一起落实的算法／Agent 语义 |
| --- | --- | --- |
| 查询理解／Ontology 使用 | Search 的 internal/search 或推荐场景用例；语义理解接本域 Agent | 输入如何改变查询、范围、候选或排序；保留用户原始意图和实际使用路径 |
| 新召回通道 | 本域召回组合 + `common/retrieval` 对应全文、内容图或向量后端 | 候选单位、独立召回、分数含义、范围过滤、通道预算及融合方式 |
| 新特征／更换表示 | 内容加工／embedding／特征使用者 + 所属算法模型 | 来源、计算时点、缺失含义、训练与在线一致性；表示变化同步索引 |
| 排序／重排 | Search 排序／common/inference + 推荐目标选择 | 搜索与推荐目标、特征输入、模型加载、列表约束与相同数据上的效果比较 |
| 广告匹配／预估 | 任务明确的候选策略与算法所有者；复用确有相同语义的算子 | 可投范围、标签与预估目标单独表达，不把自然推荐分数当广告预估或竞价结果 |
| 问答／计划／工具推理 | 本域 Agent、Tool、Prompt、Graph 与 Runner 的真实装配 | 算法工具返回证据，Agent 消费证据；预算、引用、不足状态和最终结构化结果 |
| 内容理解／物品建模 | Async content／processing + 实际 Worker 任务 | 完整来源、自然结构、实体关系、原文位置、质量／时效特征及增量恢复 |
| 索引／检索后端 | 离线编码和构建 + common 检索 + 在线查询端 | 编码与度量一致、子表示到物品映射、更新删除、模型与索引同时切换 |
| 反馈／样本／训练／评测 | BTW content、analytics 及 DataCenter 模型运行端 | 曝光与反馈关联、标签来源、数据隔离、目标函数、导出加载与效果证据 |
| API／JSON／SSE | 对应契约及原工程映射／交付位置 | 算法输入确实参与计算，分数与路径真实，流式终态包含同一业务结果 |
| 存储／配置／部署 | 数据所有者、实际装配与涉及的配置／deploy | 支撑上述算法的数据与资源，不把地址或变量存在当成模型／索引接入 |
| 简化计算／去掉中转 | 迁移实际消费者并收拢共同计算 | 结果语义与必要保证保留，重复编码／计算／状态退出；保持 go-zero 组织 |

[能力落地规范](references/writing.md) 给出每类实现、配套数据和效果验收。只改内部算法时不必新增 HTTP/RPC；接口变化时仍从 `api/btw.api` 生成，不手改生成物。

## 新增功能的规范

新增功能以一个明确的搜广推目标或 Agent 任务为单位完成，包含它实际需要的数据、算法、装配和验证。

1. **定义目标与样本。** 说明要改善搜索相关性、推荐匹配、广告预估、内容理解还是 Agent 交付；给出能够暴露旧行为不足的查询、场景或资料。新能力没有历史基线时明确记录，不预设一个模拟提升。
2. **确定输入和产物。** 明确使用哪个查询／Ontology／场景、物品范围与原文版本，返回候选、特征、分数、模型还是带引用结果。向量注明表示空间，分数注明含义；只为真实边界保留必要合同，不增加逐层 hash／登记协议。
3. **按职责落位。** 搜索理解与相关性进 Search，推荐策略与目标进 Recommend，内容和离线生产进 Async；相同表示／检索等机制可进入 common。Agent 在本域组合这些能力。广告任务按实际领域归属实施，不因名称建立空服务。
4. **按两边框架规范实现并接入实际算法链。** 新通道加入召回组合，新特征接入生产与消费，新模型接入加载和排序，Tool 注册到实际 Agent 并调用已有算法。普通确定性计算直接执行；没有消费者的文件、注册项和工厂对象不算新增功能。
5. **闭合离在线依赖。** 需要数据或训练的能力同步样本、标签、特征处理、模型产物及在线使用；表示变化同步物品索引。已有产物复用，不在搜索、推荐和 Agent 侧重复理解同一内容。新能力需要的配置、协议与 Worker 启动一起接通。
6. **同时验证正确性、效果和代价。** 功能测试证明输入、范围、分数与终态语义；效果评测使用相同条件的样本和基线；按改动记录延迟、吞吐、资源或模型调用成本。没有真实数据／模型时明确未验证的结论，不以替身或写死分数宣称提升。
7. **完成替换与交付。** 记录实际选用的策略、模型和索引及测试条件；替换旧实现时退出其专属装配与配置。扩大数据规模、在线实验和部署只按本次授权推进，不由一次本地评测自动触发。

新增能力子包保留在所属域现有 internal 下；新增 common 能力须有真实跨域消费者和相同语义。不要为每个算法步骤拆服务或 Graph 节点，也不要为“可扩展”预建注册平台。

### 本项目中的新增功能例子

- **新增学习型 Sparse 召回**：补文档／查询稀疏表示与对应倒排后端，明确它的评分语义；通道独立产生候选并进入融合；评测稀有词覆盖、召回质量和延迟。不能用词频检索冒充学习型表示，或仅对 Dense 已有候选打分就称为新增召回。
- **替换推荐排序模型**：补真实样本与特征处理、训练／评测、模型导出和 runtime 加载；用同一候选集合比较排序质量，再分别观察召回变化的影响。不能只换模型名或固定加权分。
- **新增有据计划 Agent**：根据 Ontology 和场景组织需求，调用现有检索／原文工具取得证据，在本域 Agent 中生成计划与引用；验证证据不足、工具失败、取消和最终结构化结果。检索与排序仍复用原算法实现。

## 解耦与框架依据

执行 [解耦规范](references/decoupling.md)：能力与状态有明确所有者，共同计算复用有效产物，场景策略与技术实现分开；不以重复转发、重复编码或影子状态代替模块边界。

编码前按 [go-zero 开发规范](references/go-zero.md) 和 [tRPC-Agent-Go 开发规范](references/trpc-agent-go.md) 实际加载原始来源，再按 [联合开发规范](references/framework-integration.md) 完成本项目的衔接。具体 API 使用项目解析版本；框架细则、BTW 应用约定与当前装配事实分开标明，不另写通用命名教程。

- 调整进程边界或取消 RPC 中转时，按当前用户目标改实际调用方式，保留 go-zero 工程职责；现有目录不要求保留无用的运行环节。
- 回退、删除、备份及发布使用 [改动与回退规则](references/change-control.md)。
- 架构图及产品方向使用 [架构语境与图解规则](references/architecture-context.md)；图内只用通用概念，历史方案不是当前功能。
