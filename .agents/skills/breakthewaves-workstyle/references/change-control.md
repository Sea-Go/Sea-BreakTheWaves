# 改动、删除与回退

## 任务范围与工程约束分开记录

| 用户要求 | 应执行 | 不能自动推导出的授权 |
| --- | --- | --- |
| 画当前架构、查看实现 | 读取源码、生成对应图文 | 改代码、修缺口、部署 |
| 改功能、修问题 | 修改该能力的完整调用链和必要契约 | 搬整个仓库或换工程规范 |
| 大范围重构、允许新接口 | 在明确目标下分完整能力推进 | 取消 go-zero、批量删除仍有效的约束 |
| 合并进程、取消 RPC 中转 | 改已授权的调用或部署拓扑 | 取消 `.api`、生成链或标准分层 |
| 只恢复目录、保留功能 | 还原布局与必要 import/构建引用 | 把业务实现一同 reset 掉 |
| 回到某提交、撤销整轮改动 | 核实范围后按 Git 恢复 | 清理其他项目、私有配置或数据 |
| 不要备份 | 本次不建立备份或补丁副本 | 放弃保护范围外已有修改 |

授权边界已清楚时直接完成，不逐步索要确认。只有影响重构结果、功能保留或数据去留的歧义才需要澄清；说明歧义及具体差异。

## 重构和删除

- 先证明要删除的层、契约、状态或计算的生产者和消费者，说明替代后的行为及失去的兼容性。
- 按完整能力迁移和验证。领域改动与工程布局变更分别评估，不把“采用新版本”视为整树重写许可。
- 目录、生成方式、包边界和既有测试是当前约束。若业务目标需要改变它们，先识别该变化是否已经得到明确授权。
- 用户允许删除的旧能力应完整收口，不保留无意义影子实现；仍有职责的代码留在其所有者中，不为缩短路径移入全局共享包。
- 干净临时工作区适用于隔离并行变更；不丢弃当前任务已授权且需要继承的修改。交付时明确改动实际位于哪个工作区。

## Git 恢复

恢复前只读核对当前提交、目标提交、已暂存/未暂存差异和未跟踪文件。目标从当次对话和 Git 证据确定，不把历史提交固定成永远正确的回退点。

- **限定范围恢复**：使用路径限定的 `git restore --source=<目标> -- <路径>`；是否恢复暂存区取决于用户要求，不能顺手清空无关暂存内容。
- **已明确授权整轮/整仓回退**：可以使用 `git reset --hard <已核实目标>`。它同时还原代码和目录；先确认待丢弃内容属于授权范围，并核对占用目标路径的未跟踪文件可能被覆盖，不用继续手工搬迁模拟回退。
- **新增文件**：reset 不删除普通未跟踪文件。逐项列出本任务新增的可删除路径再清理，保留其他未跟踪或忽略文件；不使用泛化的 `git clean -fdx` 扫过私有配置和数据。
- **备份**：遵守当次要求，不由技能自动增加备份流程。明确“不要备份”时，不创建备份目录、stash、patch 或其他形式的副本。
- **完成依据**：确认目标提交、目标目录以及 `git status`/diff。只有确实干净才能说工作区干净；“目录恢复”与“代码也被回退”必须如实区分。

如果全面回退会覆盖可辨识的范围外用户工作，应缩小到已授权路径，或只就冲突部分取得方向；“不要备份”不会扩大丢弃范围。

## 外部操作与提交

- 数据库、队列和模型测试先确认任务环境；已有凭据不代表获得生产写入、付费调用、索引清理或部署授权。
- 用户要求提交时才提交，按完整功能单元组织 Conventional Commit；中文或拆分要求遵循当次指令。提交、推送、合并和部署分别判断授权。
- 各类能力的实现位置、调用接入与完成条件见 [能力落地规范](writing.md)。
