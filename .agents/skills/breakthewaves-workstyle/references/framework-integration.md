# go-zero 与 tRPC-Agent-Go 联合开发规范

适用 BTW 的算法搜索、推荐、广告相关算法任务与 Agent 能力开发。单框架细则见 [go-zero](go-zero.md) 和 [tRPC-Agent-Go](trpc-agent-go.md)；本页规定两边在一次功能里怎样衔接。它是实现规范，不声明当前所有链路已经达到这些要求。

## 一次功能的责任划分

| 功能部分 | go-zero 负责 | tRPC-Agent-Go 负责 | BTW 算法／业务负责 |
| --- | --- | --- | --- |
| 外部合同 | `api/btw.api`、路由、类型和传输映射 | 工具 schema、模型结构化输出等内部调用合同 | 查询／Ontology／场景含义，候选、分数、引用与结果语义 |
| 输入与身份 | 解析、可信身份、领域参数传递及 Context | 本次 Run 的用户／会话、消息和输入状态 | 允许数据范围、画像使用方式和表示空间匹配 |
| 实例装配 | config、svc、进程启动／退出 | Model、Tool、Agent、Runner 及所需框架服务 | 实际算法后端、物品／原文存储、场景策略 |
| 执行 | 用例入口、协议错误和取消传播 | 模型调用、工具循环、必要编排、事件生成 | 召回、特征、排序、原文读取和权威数据提交 |
| 输出 | JSON／SSE 编码与写出 | 增量、完整消息、工具事件、运行终态 | 列表、答案／计划、证据不足及业务成功判定 |
| 状态 | 服务资源及所属持久化装配 | Session、Graph State 与声明使用的 Memory／Artifact | 完整来源、物品、样本、模型、索引和加工进度 |
| 验证 | 真实接入、字段传递、错误及公开流 | 工具执行、编排、事件、隔离与生命周期 | 算法效果、引用支持、数据恢复与资源代价 |

边界是职责，不是要求每个格子增加一个包、DTO、Agent 或网络调用。当前统一 API 直接调用领域公开能力，Worker 直接调用内容能力；没有内部 RPC 中转。

## 输入输出怎样穿过两边

1. **接口输入进入领域请求。** 在 `api/btw.api` 表达本次需要的查询、Ontology、场景、结果数量和请求关联信息；生成类型由 API logic 映射到领域输入。已有接口缺少字段时按任务补齐，不声称旧合同已支持新能力。
2. **用例确定范围与预算。** 服务器配置的场景决定允许物品、算法策略和计算预算；可信身份与数据范围由宿主控制。用户文本、Ontology 属性及模型生成的工具参数不能扩大它们。
3. **执行路径按任务选择。** 列表直接走算法链；语义任务将目标、当前上下文和所需证据传给本域 Runner。Agent 从实际工具集合调用同一检索／排序／原文能力。
4. **模型结果回到业务合同。** 过程增量用于展示；完整结果解析为答案／计划等业务对象。引用要指向实际取得的原文位置，模型错误、不足或取消保留对应含义。
5. **业务结果回到协议。** 普通结果映射为生成响应；流式结果形成稳定业务事件再交给 JSON／SSE。相同调用的最终 JSON 与流式终态必须描述同一份结果。

领域算法不依赖 HTTP writer、pb 消息或整个 svc 容器。Agent Tool 不回调自身公开 HTTP 接口来重复鉴权／解析／序列化；确有跨进程所有权时才使用已有公共 client。当前同进程能力直接复用。

## 配置预算状态与生命周期

### 配置映射

| 内容 | 装配时怎样传 | 运行时怎样使用 |
| --- | --- | --- |
| HTTP 配置 | 本域 config → go-zero server | 影响连接、传输、中间件与生效的 deadline |
| 生成模型与工具集合 | DataCenter manifest 公布逻辑别名 → BTW 构造 tRPC-Agent-Go 受控客户端 → 本域 Agent factory／Runner；工具与策略预算留领域 | 部署层提供可轮换服务身份，BTW 只配置 DataCenter 地址；每次请求不修改共享 Model／instruction／工具 slice |
| 场景预算 | 场景配置 → 用例总期限、候选预算及框架调用限额 | 每层在剩余预算内执行；只设置 Agent 局部次数不等于限制整个业务 |
| Ontology／当前证据 | API mapping → 本轮领域输入／Run 消息或状态 | 只属于当前调用，不写到共享 runtime 的“当前用户”字段 |
| Session 后端 | 应用创建并传入实际 Runner 服务选项 | 按 app/user/session 隔离；持久化与内存行为如实报告 |
| 模型／索引配置 | 当前部署的加载端与配置选择 | 相同请求使用匹配的模型、表示、特征和索引；不在请求中扫描全量工件自检 |

HTTP、算法调用和 Agent 使用一条有效的取消链。当前链路长流要核对各层路由、拦截器和连接设置，不把 go-zero 普通请求超时直接当成模型总预算。模型、Tool 与 SDK 的重试在总预算内由明确位置负责。

### 状态所有权

- 物品、原文、索引可见性、反馈与任务状态由对应业务所有者维护；业务成功取得它需要的真实提交结果。
- Session 记录会话／事件；Graph State 组织当前工作流；它们不能再各维护一份“当前内容加工成功”或外部用户画像权威状态。
- Runner completion 不是通用事务提交凭证。若接口承诺同步持久化，必须从对应存储获得确认；若只是接纳任务，返回接纳状态，不假称全文已加工或索引已更新。
- Framework Session schema 与业务 GORM schema 各由所属实现管理。当前公共 Session helper 使用内存后端；上线持久后端需要实际装配和验证。

### 关闭顺序

应用 owner 负责停止接纳新工作，向其跟踪的前台运行／Worker 发出取消，并等待这些工作按预算退出；随后关闭 Runner 及由应用拥有的外部 Session、MCP、HTTP／数据库等资源。具体顺序按资源依赖落实：正在借用存储的任务退出后才能释放该存储。

框架 Close 不承担应用所有 goroutine 的等待，go-zero 服务退出也不自动关闭 Runner。每次请求只取消自己的运行，不关闭共享 Runner／连接，不关闭框架生产的 channel。调用方取消后确需继续的工作必须进入正式后台任务及其持久状态，不能悄悄脱离请求。

## 错误终态与跨进程事件

### 统一业务判断，分别处理传输

| 发生的情况 | Runner／领域侧 | RPC／HTTP／SSE 侧 |
| --- | --- | --- |
| 请求或场景不合法 | 不启动昂贵算法／模型 | 返回项目合同中的输入失败 |
| Run 启动失败 | 保留准备／模型等失败原因 | 输出前可用普通错误；不进入等待空流的循环 |
| 没有足够证据 | 形成明确不足结果，保留已有可用引用 | 正常表达不足，不把它伪装成系统异常或编造答案 |
| 可恢复中间错误 | 按明确策略继续，记录真实使用路径 | 中间过程可以展示；不要提前标整个任务成功／失败 |
| 终态模型／工具失败 | 保留终态原因，后续 completion 不抹除 | 尚未输出则映射错误；已输出则发送协议失败终态后结束 |
| 客户端取消／写出失败 | 取消本次工作并由 owner 收尾 | 已断开的连接不再强发终态，服务端保留取消／写出失败事实 |
| Runner 完成 | 检查业务结果、错误、取消及必要提交 | 仅满足业务成功条件才输出成功终态 |
| RPC EOF／channel 意外关闭 | 未获得预期终态时为中断或结果未知 | EOF 不是自动成功；区分传输错误与正常结束 |

这些是语义要求，优先复用当前业务状态，不要求再造一套通用状态机。

### 事件转换要求

- 保留请求、invocation／作者及事件类型所需的关联，避免多 Agent、重试或多个工具的增量串线。
- 模型 Delta、完整 Message、工具结果、Graph 输出与 Runner completion 按各自合同消费。最终文本替换对应累积展示结果，不能把全文再追加一次。
- 领域事件承载过程和最终结果，API 直接写出 SSE；普通 JSON 与终态使用相同结果。新增过程事件同步 `.api` 和映射，不能丢弃事件后声称提供完整框架流。
- SSE 使用正确事件帧和 JSON 编码；不以 protobuf 调试字符串输出 JSON。写入／序列化失败进入错误收尾，终态不能因无界缓冲或“满了就丢”而被静默丢弃。
- 内部 Runner 根据本版本完成边界结束消费；外部验证继续读取公共 SSE 到 EOF，并检查完整结果、引用和结束状态。AG-UI 或其他协议适配若采用框架模块，挂入现有服务入口，不另起重复 HTTP 服务。

## 新增功能的联合实施范式

### A. 新增召回通道或调整列表排序

1. 在 Search 检索／Recommend 场景 等所属能力实现算法，共用后端进入 common；落实候选、范围、特征和分数语义。
2. go-zero 侧在真实 svc／runtime 中接入新实现与配置；仅当输入输出改变时修改 `api/btw.api` 和映射。
3. 没有模型语义任务时不新增 Agent。已有 Agent 需要访问此算法时，复用同一实现提供 Tool／Knowledge 适配，并加入实际工具集合。
4. 从列表入口与相应 Tool 验证同一范围和算法行为；离线比较候选覆盖／排序效果及延迟。不能因工具注册成功就宣布新算法生效。

### B. 新增有据问答

1. go-zero 合同表达问题、Ontology／场景、结果数量与答案／引用／不足状态；流式能力按需要增加SSE 路由与领域事件交付。
2. Search 用例先确定物品范围与预算；本域 Agent factory 接入模型、Prompt、搜索与原文工具，Runner 使用该 Agent。
3. Tool 调用既有检索和原文能力；Agent 取得证据后输出结构化结果。选择支持工具的结构化输出方式，或明确分成取证和生成阶段；不能误用禁用工具的输出选项。
4. 领域将实际业务结果／事件映射出去，API logic/handler 负责 JSON／SSE。测试真实取证、引用回读、不足、模型失败、写出失败及取消，并验证没有跨越场景范围。

### C. 新增场景计划推荐

1. Recommend 用例按 Ontology 与场景复用召回、特征、排序；策略和允许数据范围属于推荐域，基础算子不识别网站／桌宠名字。
2. 需要计划生成时再组装本域 Agent 与证据工具。若需多个专家，明确返回父 Agent、接管当前轮或图内汇合的机制；不要为了角色名称增加多 Agent。
3. go-zero 契约与映射交付计划名称、目标、步骤、引用及展示内容；模型／工具预算和场景配置进入真实 runtime。
4. 分别验证算法筛选与 Agent 生成：不同 Ontology 如何影响候选／计划，引用是否支持建议，工具失败／不足如何交付。当前范围不直接创建外部任务或日历。

### D. 新增离线内容理解步骤

1. Async 接纳接口／消息将原文件或正文保存到业务来源存储，content/catalog 维护加工状态并由 Worker 消费；不在 HTTP 请求中等待整本书加工。
2. 解析、去重等确定性步骤使用所属实现；语义抽取由 Worker 装配 Model／Agent／必要 Graph。按自然结构读取并聚合，完整覆盖与未完成状态由内容所有者记录。
3. Agent 返回有原文位置的内容理解产物，内容链保存后交给表示／样本／索引消费者；Session／Graph checkpoint 不能替代这次业务提交。
4. 同时验证 Worker 取消／恢复、重复输入、失败产物与引用位置；如果换 Session 后端或模型，验证真实装配和资源释放。框架在 Worker 内使用，不需要额外建一个 API→Agent→RPC 转发链。

### E. 替换表示或排序模型

1. 所属训练任务生产真实样本与模型产物，特征／表示处理与在线推理保持一致；外部用户塔不在此更新。
2. go-zero 配置与 svc／runtime 加载端切换模型及相关索引；输入输出不变时保持既有接口。
3. tRPC 侧只调整受影响的 Model／Tool／Knowledge 依赖，保留场景 Prompt 和工具合同中仍成立的语义；不要让 Agent 通过编造分数补偿模型缺失。
4. 验证导出、加载、消费者生效，按相同数据比较效果与资源；模型配置存在、训练器接口实现或一次 API 返回均不等于模型替换完成。

## 联合验收与来源

| 验证面 | 必须能回答的问题 |
| --- | --- |
| 契约与接入 | 新输入是否从 go-zero 入口到达算法／Agent？最终结果与引用是否返回调用者？ |
| 装配 | 当前运行入口究竟使用哪个模型、索引、Agent、工具集合和 Session 后端？ |
| 框架行为 | Tool 是否实际执行？Graph 是否传对证据？局部完成是否误结束？取消是否传播？ |
| 状态与资源 | 谁提交业务状态？谁关闭 Runner 与外部依赖？恢复是否重复副作用？ |
| 算法与任务效果 | 在什么样本、候选预算和模型条件下，相关性／匹配／证据支持发生了什么变化？ |
| 公开协议 | 普通响应与流式终态是否一致？公共流到 EOF 后能否识别成功、失败或中断？ |

只运行本次修改需要的验证。框架替身用于可重复的行为测试，真实模型、真实存储、效果评测和生产规模分别取证；文档编辑不运行整套业务环境。

来源与版本事实由 [go-zero 细则](go-zero.md#规范来源与版本核对) 和 [tRPC-Agent-Go 细则](trpc-agent-go.md#必须实际加载的原始规范) 维护。本页的功能分工与接入范式是 BTW 项目约定，不冒充任一框架对所有应用的强制架构。
