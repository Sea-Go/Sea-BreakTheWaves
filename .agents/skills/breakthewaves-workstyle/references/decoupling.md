# 解耦规范

本项目解耦的重点是把**表示与检索算子、场景目标与排序策略、Agent 语义任务、离线数据生产、外部用户与来源系统**分清，同时让同一算法的数据准备和计算保持内聚。实现保留原有 go-zero 工程组织。

## 算法与 Agent 的职责边界

| 边界 | 必须保持的分工 | 需要消除的耦合 |
| --- | --- | --- |
| 用户侧与物品侧 | 外部提供 Ontology／用户表示；BTW 维护物品、候选和算法产物 | 搜索或推荐为了执行一次请求又重建用户画像／用户塔，或隐式依赖外部私库 |
| 内容与在线检索 | 离线产生可追溯内容、关系、特征与索引；在线消费适用产物 | 每次请求重新解析原书、重新理解同一内容，或扫描全量历史生成特征 |
| 表示与存储后端 | 语义来自模型、表示空间及度量；后端负责对应索引读写与查询 | 换后端后悄悄换成另一种评分，却仍宣称同一算法 |
| 共享算子与业务目标 | 复用相同检索、编码、特征计算；搜索、推荐、广告各自持有目标及策略 | 在通用检索里判断场景名称，或把一个分数同时称作相关性／点击预估／广告价值 |
| 算法与 Agent | 算法提供候选、特征、排序及原文工具；Agent 理解需求、取证和生成 | Agent 再写一套召回排序，或算法必须穿过多层无决策作用的 Agent 才能执行 |
| 训练与在线使用 | 特征处理和模型／索引语义一致；训练在离线任务，推理在实际消费者 | 训练器与线上各算一套特征，换了查询模型却继续查询旧表示索引 |
| 观测与业务状态 | 实际调用处记录路径、样本条件、用量与错误；提交由原所有者负责 | 为统计再造一次状态流转，或把候选生成计作曝光、把日志计数计作模型效果 |

这些边界约束职责，不要求各拆一个服务。同一查询的编码在模型空间与输入相同时可复用；同一内容理解在来源修订和模型语义仍有效时可复用。不同目标、表示空间和时点不能为了共享而混为同一产物。

## 1. 依赖方向与模块接口

新增实现遵守下面的依赖方向。“可依赖”列给出该层允许使用的对象，不要求每次调用都经过表中所有位置。

| 实现位置 | 可依赖 | 不得依赖 |
| --- | --- | --- |
| API handler | 本域 logic、传输类型与 go-zero HTTP 能力 | 存储、排序器、模型 SDK |
| API logic | 领域公开能力、mapping 与注入依赖 | 业务数据库、其他域 internal |
| 领域公开入口 | 本域 internal 和必要公共合同 | 其他域 internal、HTTP handler |
| 领域算法 | 所需值类型、纯计算、必要消费者接口 | svc 容器、完整配置、HTTP 请求对象、外部项目数据库类型 |
| 存储／模型／外部协议适配 | 外部 SDK、本域合同 | handler、整个应用流程 |
| common | 标准库、共享技术依赖、稳定值类型 | search、recommend、async 业务域 |

跨域约束以现有架构和 `service/boundary_test.go` 为准：search 不引入 recommend/async；async 不引入 search/recommend；recommend 不引入 search/async 的 internal。API 是组合所有者；其他域不能反向依赖 API，common 不反向依赖任何业务域。不得移动测试或把业务塞进 common 来绕过这些限制。

接口设计必须让调用者只提供业务输入，并获得结果或明确失败。同一能力内部的准备、计算和结果组织由实现自己完成；调用者不负责按顺序执行 prepare/register/hash/validate/execute 等内部步骤。确有不同生命周期或持久化语义的操作才独立暴露。

正例：一个检索能力接收查询、范围和预算，完成所需数据准备并返回候选。反例：调用者先创建全局工件、登记版本、冻结状态，再凭内部句柄启动一次本可完成的纯计算。

解耦时按实际问题修改代码：

| 出现的耦合 | 必须写出的改动 |
| --- | --- |
| 算法读取外部项目专用表／SDK 结构 | 将读取与转换收进已有适配器，算法使用本域输入与最小依赖 |
| 多处写“当前状态”并互相修补 | 保留一个权威写入者；只读投影标明来源与更新责任 |
| 多个入口重复读取和理解相同正文 | 把相同计算合到一个能力，复用有效产物；场景目标仍分开传入 |
| 深层函数临时找配置／连接数据库 | 将所需配置及实例从 svc／工厂显式注入 |
| SDK、Tool、业务层同时重试 | 保留一个负责幂等与总预算的重试位置 |

## 2. 小接口承载完整能力

一个模块的接口应让调用方知道：给什么输入、得到什么结果、哪些失败需要处理、是否产生副作用。不要求调用方参与模块内部的每一个计算步骤。

- 传递本次计算真正需要的字段和最小依赖，避免传全局容器。go-zero logic 可以按规范持有 svc，但不把整个 svc 上下文继续传给每个领域算法或 Tool。
- 已知结构使用具名类型；只有真正动态的数据才使用开放字段。不要把一份巨大可变 map 当成全部模块的共同状态。
- 依赖外部系统时，将变化留在明确的 Adapter（适配器）位置。项目已有客户端/适配器满足需求时直接复用，不再套同义接口层。
- 单实现、同进程的纯计算优先普通函数或具体类型。真实生产替换、远程隔离或测试替身有需要时，再引入最小 Interface（接口）。
- 为每一层说明它独立承担的责任。删除这一层后复杂度也随之消失，通常可以合并；删除后责任散落到多个调用方，则需要保留或收回到权威所有者。

模块、接口和替换位置的详细方法可按需要读取现有 `$codebase-design` 技能；不把这些概念机械转换为更多目录和微服务。

## 3. 计算高内聚，策略保持独立

- 一份数据在一个能力内完成必要准备、计算与结果组织；相同输入的昂贵产物在有效范围内复用。只有确有复用收益才加缓存，并说明何时失效。
- I/O、算法和交付各有责任，但不为每次函数调用增加 DTO、网络中转或 Agent。网络调用由实际部署或所有权要求决定。
- 共享召回、特征和评分机制，不把搜索相关性、推荐场景、数据范围与交付形式混成一个总规则。
- 对可变化的模型、预算、阈值和策略使用现有配置机制；对固定业务不变量用直接代码。把常量搬进配置文件并不能自动消除业务耦合。
- 如果外部已经负责用户状态或表示，本域消费其合同，不为了“独立运行”再维护一套同名权威状态。职责迁移只按本次明确目标执行，不能从历史方案推定。

## 4. shared / common 的边界

进入 common 需要稳定语义和实际消费者；名称相似或出现两份代码并不足以说明应共享。

- 合适：已有通用协议适配、基础数值计算、观测设施、稳定跨域值类型。
- 不合适：某个场景的决策、完整应用流程、领域状态写入，以及为了绕过 `internal` 限制搬来的业务集合。
- 共享实现不反向依赖具体业务域；域间依赖遵循现有公开契约及仓内 import 规则。
- 用同一实现消除已证明的重复，不以抽象为名增加注册中心、插件系统、流程引擎或“未来可能用到”的多后端。

## 5. 状态、资源与必要校验

对有状态、异步或外部写入的改动，说明谁创建、谁拥有、谁提交、谁重试、谁取消、谁关闭。纯计算不因套模板而增加状态机。

- 同一进程、同一信任边界内复用已完成的输入归一化与提交结果；消费者不重复登记或确认。跨权限主体、跨租户或新的外部入口仍由该入口执行必要授权，不能把解耦写成跳过权限。
- 重试针对可恢复失败，并受幂等性、取消和预算约束。已成功的不可变产物按实际恢复需求复用，不让恢复路径重复产生副作用。
- 同进程、已归一化的类型不在每层反复 JSON 编解码、hash、冻结和校验。必要的外部输入或模型结果处理集中在所属接口处。
- 删除检查前说明它保护的可观察保证。可以删除重复检查，不能顺手取消权限、并发、数据完整性或真实外部输入所需的保证。
- Prompt 处理语义目标，确定性代码处理明确约束；不把整个普通计算链拆成同名聊天 Agent。

## 6. 可复核的完成条件

解耦改动交付时，用简短说明回答：

1. 哪个模块现在拥有这项能力和状态？原有调用方如何使用？
2. 哪项依赖、重复计算、同步义务或隐含调用顺序被移除？
3. 哪个可变依赖能在约定位置替换，而不改核心计算？若没有替换需求，是否避免了多余接口？
4. 哪些功能或兼容性被保留、明确改变或退役？
5. 哪些行为测试证明这次收敛有效？

通过模块对外行为验证正常、失败及实际恢复场景。替身可以证明隔离能力，真实适配还需对应协议/集成证据。不要只用新增接口数量、删除行数或目录测试作为完成依据。
