# 架构语境与图解

## 先确认当前事实

统一 go-zero API 从 `api/btw.api` 生成到 `service/btw/api`，无项目发布版本路径。Search、Recommend、Async 保留各自领域边界，Worker 负责完整来源加工与 Elasticsearch／Neo4j／Milvus 检索投影；旧内部 RPC 和项目自有用户画像生产不在当前调用链中。搜索使用 fast、balanced、deep 三种实际路径，推荐仍有独立场景目标。

代码发布和整体回退由 Git 与部署平台负责。来源的修订顺序是内容业务数据，不是 BTW 自有代码发布版本。DataCenter 统一管理表示、排序与生成模型；BTW 模型运行配置只保留 DataCenter 地址，部署层提供服务身份。API／Worker 从 DataCenter manifest 获取当前模型合同，不自行选择物理模型。当前验证边界见 [验证报告](../../../../docs/architecture/validation.md)与 [搜索 Benchmark](../../../../docs/architecture/benchmark.md)：旧隔离 PostgreSQL、Elasticsearch、Neo4j、真实 BGE 与生成模型的小样本联合测试和 SciFact Benchmark 已执行；迁移后的 DataCenter 网关有双仓库适配测试，但未完成新路径的物理 Milvus／Kafka／S3／ClickHouse 联测或亿级验收。

## 项目背景与已明确的设计方向

本项目定位是算法搜广推与 Agent 系统。搜索解决查询到相关物品／证据的选择；推荐解决用户与场景到物品的选择；广告相关算法在明确任务中处理候选资格、匹配与效果预估；Agent 负责语义理解、工具取证和生成交付。内容加工、样本、训练、评测、表示和索引支撑这些在线能力。

本会话明确的方向用于新增功能的职责判断，不表示旧代码已迁移完成，也不授权在规范编辑任务中重做整套改造：

- BTW 持有搜索、推荐、Agent 和内容数据；DataCenter 持有模型配置、训练与推理。跨仓库模型合同由各自的入口和适配器连接；网站和桌宠不属于 BTW 的实现目录。
- 每次请求提供 Ontology 与可选用户表示；用户画像和用户塔生产在外部，BTW 负责物品理解、表示、检索和排序。
- 完整文本是物品和证据的基础。电子书原文件、正文、自然目录与原文位置保留；临时计算窗口与检索子表示不作为固定 chunk 推荐对象。
- 网站资料通过消息接入，保留接纳时原文和来源链接；书籍上传进入内容链，不据此扩展爬虫任务。
- 网站列表使用允许的网站物品，书籍及书内对象在召回前排除。问答／桌宠计划调用模型，以已保存原文支撑引用，计划不直接创建任务或日历。
- 搜索、推荐、广告预估分别维护目标与标签。Agent 调用算法能力并消费结果，不重复实现召回、特征和排序；仅需列表的场景不必经过生成模型。
- 广告算法属于项目背景；当前没有独立广告服务，不把它描述成已上线能力。竞价、预算与计费仍不在当前约定范围。
- 原计划的表示、排序模型和存储选型是实施基线，具体落地按当前任务和配置；不把某个模型名称或数据库写成所有场景无法替换的业务依赖。
- 亿级容量以完整物品数计量；书内节点、子向量和构建峰值另算。验证应同时报告召回／排序效果、延迟吞吐、更新成本与资源，不能由小样本外推生产 SLA。

DeepSeek 公开岗位仅能提供内容加工、搜索、索引与反馈迭代的职责参考；不得据此声称知道其内部算法、数据库或融合公式。

## 当前架构图如何画

- 搜索与推荐分别成图，共用的内容、表示、索引与训练基础单独说明。先定图数和层次，保留足够留白。
- 图内使用通用业务/算法名词，如“用户画像、物品、召回、融合、过滤、排序、原文、索引、大模型”。本项目图解不在节点里塞函数、类型、代码路径、接口路径、配置键或端口。
- 具体条件和细节放在图下说明：谁提供数据、各路候选如何产生、哪些阶段可选、结果怎样交付、失败如何结束。
- 用户明确要求源码定位时，可以放到独立证据说明，不让图面变成调用符号清单。
- 对“当前实现”“示例配置”“可选但未装配”“目标方向”分别标注。框架、模型或算法包存在，不能被画成已经启用的完整链路。
- 表达当前行为时，核实并行/串行、范围过滤时点、回退与错误、是否真实调用模型以及是否改变用户状态。
- HTML 应可离线阅读，放大后能看清图，目录与正文保持一致；检查桌面和窄屏布局、箭头/文字遮挡及引用链接。纯图文任务不重跑业务环境或借机修业务代码。
