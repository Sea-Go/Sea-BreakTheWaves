# 算法搜广推与 Agent 的功能落地规范

本页以查询、用户 Ontology、完整物品、候选、特征、模型、证据和反馈为工作对象。每次修改先明确要改善哪项算法目标或 Agent 任务，再落到实现、数据产物、实际消费者和效果验证。目录与接入层服务于算法链，不以增加接口或文件作为交付目标。

完整目录说明、改动位置速查及新增功能要求见 [技能正文](../SKILL.md#项目目录及职责)。每类功能同时遵守 [两边框架的联合开发规范](framework-integration.md)：协议与服务由 go-zero 接入，语义任务按 tRPC-Agent-Go 运行，算法与业务数据留在所属领域。本页展开各类业务能力的实现细节。下列位置来自当前仓库，表示能力归属，不表示其中每个实现都已启用。新增文件后必须接到实际使用的装配与调用链。已经退役的旧画像、chunk 和专用协议不能作为当前开发范式。

## 1. 算法输入、物品与候选

**适用**：增加 Ontology 使用、改变检索／推荐对象，或增加候选和结果信息。

**落到哪里**：外部合同进入 `api/btw.api` 并生成；公共值类型在 `common/item`，Search／Recommend 定义用例语义。来源和物品写入由 Async catalog 持有，不能在每个 Agent 中复制物品库。

- 一次算法输入需要明确查询或上下文、Ontology、场景范围和实际计算预算。增加画像节点、偏好或用户向量后，必须接到查询组织、召回或排序消费者，并用不同输入证明它真实影响结果。
- 外部用户向量只有表示空间匹配时才参与向量计算；没有合格向量时使用图画像或其他真实可用算法路径，结果注明实际路径。不能仅因向量维度相同就视为同一空间。
- 候选保留物品标识、召回来源和真实分数；书内信息或子向量保留父物品与原文位置。融合去重时聚合正确对象，不丢失出处，也不把子表示数量当成物品数量。
- 新增相似度、相关性、预估概率或重排得分时，写清各自含义和消费者；不能将一个数复制到所有分数字段，也不能把未校准的相似度当点击概率。
- 只在跨外部接口、存储或模型输出的真实边界转换和检查。内部已明确的数据直接传递；不要求建立新的冻结、登记、hash 或逐层验收合同。

**完成条件**：从真实入口证明范围、Ontology 和其他新输入参与了对应计算；返回对象与分数具有约定含义、可定位来源。算法只在内部变化时不必新增协议。

## 2. 查询理解与多路召回

**适用**：查询改写、意图识别、增加召回通道、候选融合或更换后端。

**落到哪里**：检索组合在 `service/search/rpc/internal/search`；推荐场景在 `service/recommend/rpc/internal/recommendation`，复用同一候选能力。共同后端在 `service/common/retrieval/items`。

- 查询理解产出可执行的检索条件或查询表示，保留原查询和已授权范围；模型扩展查询不能扩大数据权限或改变用户明确的排除条件。评测既看相关性增益，也看改写造成的漏召回。
- 新通道必须独立产生候选，再进入本域融合。学习型 Sparse 的编码与稀疏度量要真实一致；多向量若定义为召回通道，要独立检索子表示并聚合到物品，不能只对 Dense 候选重排。
- 配置通道预算、后端过滤和候选映射；必要范围在召回前下推。证明后端实际执行该条件，不能在返回列表删除若干结果后宣称“未召回”。
- 融合明确是按排名、归一化分数还是已训练的融合器组织。不同通道的原始分数未必同尺度，不以随手添加业务权重替代算法选择；保留来源以便测量每路贡献。
- 一个模型空间内可共享查询编码与读取产物；不同空间分别编码。召回只向后提供候选与证据位置，不负责生成推荐解释或维护用户画像。

**完成条件**：新通道接入实际搜索／推荐 runtime；使用相同语料、范围、查询及候选预算比较单路和融合后的覆盖、Recall@K 等适用指标，同时记录延迟与候选数量。小规模精确计算可作离线数值对照，不加入每次在线请求的必经链。

## 3. 特征、排序与场景重排

**适用**：增加特征、替换粗排／精排／重排模型，或增加推荐场景。

**落到哪里**：特征定义在 `common/ranking`，真实模型推理在 `common/inference`；Search 执行搜索／推荐对应排序目标，Recommend 持有场景交付。新增阶段须有质量或资源收益。

- 新特征同时写清来源、计算时点、缺失含义和消费者。离线样本与在线推理采用一致处理，涉及时间的特征不能使用预测时刻之后的信息；不拿任意固定分填补缺失特征。
- 搜索排序针对查询相关性，推荐排序针对明确的用户／场景目标。即使共享模型执行设施，也分别管理样本标签、训练目标、特征与评测，不把一套分数改名后用于所有场景。
- 模型替换要进入实际加载和策略选择；定义候选输入、特征顺序及模型输出语义。采用模型推理就必须真实加载产物，不能通过固定权重、分数偏移或模型名称模拟已训练排序。
- 列表重排负责本场景需要的去重、多样性、已曝光内容处理或其他明确约束。区分相关性模型和列表策略，测量策略带来的收益与相关性损失；不把所有列表约束塞进 Prompt。
- 场景指定数据范围、候选预算、排序目标和交付形式。列表直接交付算法结果；有据问答／计划把入选证据交给 Agent，不让生成文本反过来凭空创造候选或权威分数。

**完成条件**：同一候选集合上比较模型／策略排序结果，按目标选择 NDCG@K、MRR 或具备标签的预测指标；候选集合变化单独分析召回影响。没有真实曝光与实验数据时不宣称点击／转化提升。证明新特征进入模型、新模型影响排序、新场景实际使用相应范围与策略。

## 4. 内容来源与离线加工

**适用**：新增内容事件、文件输入、正文解析、内容理解、物品关系或加工步骤。

**落到哪里**：Kafka 接入、任务编排与原文公开能力在 `service/async/rpc/content`，GORM 状态在 `internal/catalog`，解析与理解在 `internal/processing`；运行入口在 `cmd/worker`，HTTP 上传走统一 BTW API。

**怎样接入**：

- 新来源先转换成 BTW 所需的来源、修订、操作及正文／对象引用，再交给同一内容加工能力。外部项目的事件结构留在接入适配处，不传遍内容处理链。
- 原始资料接纳、解析、理解、产物和索引之间直接传递已产生的数据。内容理解应产出任务所需的摘要、主题、实体关系、质量／时效特征或训练依据，并关联完整原文位置；摘要不能替代原书。普通规范化直接计算，语义抽取使用真实模型或 Agent，不为每个清洗步骤建 Agent。
- 一本书可以按自然结构分批理解并聚合，状态要表达覆盖范围与未完成部分；不静默截断。网页修订、重复来源和删除保留原始出处关系。已完成的昂贵理解在输入和模型语义仍有效时复用。
- 有持久化要求的输入先落实存储和加工状态，再按约定确认消息。把重复、更新、删除及旧修订处理写进实际状态变更；失败后由 Worker 重试所需步骤。
- Worker 的实际任务选择、依赖装配和停止逻辑一起接通。模型处理失败、解析不完整必须留下真实状态，不能把空产物标记为处理成功。

**配套与完成**：同时写来源适配、内容产物、存储、任务接入及对应配置。验证一份资料从接纳到被下游使用的完整过程，以及本次涉及的重复／乱序／失败恢复。已经退出的 chunk 和外部专用任务不得重新引入；对象粒度与外部责任按本次需求落实。

## 5. 表示生成与索引

**适用**：接入 embedding、增加 Dense/Sparse/多向量表示、调整索引构建或更新方式。

**落到哪里**：表示服务复用 `service/common/inference`；通用检索与索引后端放 `service/common/retrieval`；内容到表示、索引的加工组织留在 Async 的 `content` 和 Worker。物品／来源归属由内容所有者维护。

**怎样接入**：

- 表示变化同时覆盖离线编码和在线查询编码；明确两边使用的模型、维度及表示空间，接到对应的写入端与查询端。仅改在线模型配置不能继续假定旧索引匹配。
- 新索引后端实现写入、检索以及本次需要的更新／删除，再由 Worker 和在线检索装配使用同一套对象与表示约定。模型 SDK 或数据库细节不进入场景策略。
- 多向量等子表示保留所属物品映射，返回候选时聚合回调用者所需对象。临时计算窗口不因索引实现方便而自动成为新的推荐物品。
- 更换现有模型或索引时，写清构建、可用性判定、选择新版本和失败恢复如何执行；由 Git 和部署层管理模型／索引整体切换，避免再造一层只用于登记／比对的协议。

**配套与完成**：一份新内容能完成编码、写入，并被实际在线入口检索；更新与删除在约定时间和范围内生效。效果及容量报告只写实际使用的数据量与资源，不把小规模示例称为亿级验证。

## 6. Agent 理解、取证与生成交付

**适用**：查询意图 Agent、证据问答、场景计划、内容理解，或与之配套的 Tool／Prompt／Graph。

**落到哪里**：在线证据工具／生成在 Search 私有能力，Recommend 选择计划交付；离线理解在 Async processing。共享框架技术在 agentx。详细装配见 [Agent 能力落位](trpc-agent-go.md#agent-能力落位)。

- 先定义 Agent 负责的语义任务：理解查询、选择取证步骤、解释证据还是生成计划。任务能由既有算法确定性完成时直接调用；Agent 不重新实现召回、特征和排序，也不能绕开场景数据范围。
- Tool 连接现有检索、排序或原文能力，返回物品、真实得分和证据位置等可消费信息。Agent 可以迭代选择查询与工具，但不只把搜索结果标题重新包装成“原文证据”。
- 问答与计划在候选排序后按需读取已保存原文，再组织证据。引用携带可回读的位置；没有充分证据时产生明确不足结果。模型可表达建议，但不能伪造物品、出处或完成外部任务的状态。
- Prompt 组织目标、Ontology／上下文、证据和输出合同。必要权限、硬范围与确定性列表约束由实际执行代码落实；用户和内容中的文本不成为新的工具权限。
- 工具调用次数、模型调用与总时限由场景预算和框架装配控制。重复取证复用已取得资料；Graph 只用于确需状态依赖的流程，普通顺序调用不机械拆成节点。

**完成条件**：证明实际模型／Tool 调用及证据消费，评测任务成功、引用可回读与支持性、证据不足和结构化输出；记录模型／工具失败、取消、调用次数、实际 usage 与耗时。模型 usage 未知则记录未知，不模拟成本。公共最终结果与流式终态一致。

## 7. 反馈、样本、训练与评测闭环

**适用**：增加反馈事件、构造样本、训练物品表示／排序模型、发布模型及比较效果。

**落到哪里**：反馈接纳和候选 outbox 归 content/catalog；ClickHouse 聚合在 `common/analytics`；采样由 content 组织，真实训练和物理模型装载归 DataCenter，BTW 的 `common/inference` 只实现其受控调用合同。

- 曝光与后续行为按请求、物品、场景和需要的模型／实验版本关联，记录实际展示顺序。服务端生成候选不等于客户端曝光；未经曝光或观察窗口尚未结束不能直接充当确定负反馈。
- 合成查询、教师判断、人工标签与真实行为分开保留来源和计数。样本应有原文或行为依据，负例策略针对目标设计；不能把随机权重导出称为训练产物。
- 训练／验证／测试按任务需要隔离完整来源、重复簇及时间，防止同一本书的近重复内容或未来行为泄漏。记录样本范围和标签口径，使基线与改动能在同条件下比较。
- 搜索表示、推荐匹配和排序目标分别训练。推荐物品塔使用外部固定用户表示时，只更新所属物品模型；缺少合格表示和行为样本就报告未具备训练条件，不伪造个性化结果。
- BTW 离线任务导出有来源隔离的样本；DataCenter 实际执行训练、装载并通过 manifest 公布当前合同，BTW 再批量编码和构建对应索引。特征处理与模型一同使用，避免新查询编码查询旧空间。
- 评测产物包括数据条件、基线、质量变化与资源代价；模型加载成功只是工程验证。在线实验按实际分桶、曝光与观察窗口计算指标，不由离线分数外推线上收益。

**完成条件**：反馈可关联，样本进入真实训练，产物导出并加载，消费者使用后按约定改变结果；质量与容量只报告实际验证范围。当前计划不迁移旧用户塔与 chunk 数据，新的物品体系从完整原文构建；原有数据库保留，不因开发或规范编辑操作旧库。

## 8. 存储、外部系统与配置

**适用**：新增数据表／字段、对象存储、外部客户端或替换已有后端。

**落到哪里**：元数据读写进入 Async catalog；共享技术为 `common/database`、`blob`、`inference`、`retrieval/items`。API svc 与 Worker 显式装配，框架 Session 不拥有业务 schema。

**怎样接入**：

- 修改数据结构时一起修改真实写入者、读取者及事务范围。一个状态由一个所有者写入，其他模块消费其结果或只读投影，不为新场景复制另一份权威状态。
- 外部接入提供 BTW 所需的能力，在适配处转换协议；业务计算不依赖外部表名、专用发布步骤或隐式用户查询。外部已有能力通过请求输入提供时，直接使用输入合同。
- 新后端必须在实际装配中被选择并注入消费者；DataCenter 管理表示、排序与生成模型，BTW 只配置其地址并从 manifest 取得当前模型合同。服务身份由部署层提供，原文和检索索引仍归 BTW；缺身份、模型后端或匹配空间时明确失败，不回退到私有模型地址。
- 应用 schema 沿用领域 GORM 管理；必要数据迁移与恢复由当前任务明确落实，不创建无关根级迁移体系，不因实现需求直接操作旧库或其他系统。

**配套与完成**：从使用该数据的用例验证读写／替换行为，确认外部实现替换不要求改核心计算。默认值和失败行为由实际使用位置统一负责，不能在各层分别兜底。

## 9. 流式交付与观测

**适用**：新增 SSE、调整问答／推荐流、记录耗时、候选路径或任务结果。

**落到哪里**：HTTP 写出在统一 API handler，业务结果由所属领域产生；agentx 转换框架事件，公共观测在 `common/telemetry`，场景决策留本域。

**怎样接入**：

- 把模型增量、工具过程与最终业务结果映射到协议约定；最终结构化结果和引用来自实际运行产物，不从已显示文本猜测重建。
- 同一入口贯通取消：客户端结束、模型失败、任务失败分别形成可识别终态，通知本次运行停止并由 owner 收尾。局部模型完成不能提前结束整个多步骤用例。
- 观测附着在已有调用／提交位置，记录实际路径、错误与资源消耗。纯日志或追踪不新增业务状态，不改变默认执行结果，不生成模拟成本。

**配套与完成**：消费公共流到 EOF，检查完整结果、引用、失败和取消；普通 JSON 与流式终态表达同一业务结果。观测验证应证明实际运行发生，不能只证明埋点名称存在。

## 10. 合并、删除与调用方式调整

**适用**：去掉重复 Agent／包装、合并计算、取消多余 RPC 中转、迁移能力所有者。

**怎样落实**：

- 将共同计算归入正确所有者，再把真实调用方接到该实现。保留场景各自的数据范围和策略，不把整个搜索／推荐流程搬进 common。
- 同一能力内部直接复用输入和产物；删除仅改名转发、重复序列化、重复读取和重复状态。输入或存储边界需要的保证仍由对应所有者承担。
- 替换调用方式时同时处理入口装配、结果映射和必要配置；旧实现、旧依赖与仅供它使用的配置／测试在消费者迁走后移除。不要留下两条都会更新同一状态的活动路径。
- 保留 go-zero 工程组织。减少运行时服务或中转不等于把仓库改成另一套目录；源码回退、数据和发布按 [改动与回退规则](change-control.md) 执行。

**完成条件**：原有入口通过新路径得到约定行为，退役路径不再被调用；说明哪些共同修改、重复计算或状态同步被消除。文件数或接口数的变化不作为解耦完成证明。

## 11. 广告算法扩展的落地边界

本节只在具体任务要求广告相关算法时应用，不代表项目已有广告投放系统。

- 明确本次做的是候选资格、广告与上下文匹配、点击／转化预估还是其他已授权目标；每项都有自己的输入、标签和结果含义。不要将自然推荐得分直接解释为广告价值。
- 共有的内容表示、检索、特征计算和模型执行设施可复用；广告资格、标签目标及选择策略由明确的广告能力所有者持有，不嵌入通用召回后端，也不通过通用 Agent 任意改写。
- 当前无独立广告服务。优先在任务确定的领域内落实算法与调用方；只有职责和服务边界确需新增时才按 go-zero 组织扩展，不预先创建空目录或为了名称复制推荐流水线。
- 评测匹配目标或有真实标签支持的预估质量；没有广告实验数据不能宣称收益。竞价、预算、计费等仍在本会话约定范围之外。

## 不同能力怎样证明效果

以下按改动选用，不是所有任务必须跑的统一检查链，也不预设生产 SLA。

| 改动对象 | 正确性与效果证据 | 同时记录的代价／条件 |
| --- | --- | --- |
| 召回／融合 | 固定语料和过滤条件的覆盖、Recall@K；各通道贡献及漏召回样本 | 候选预算、吞吐、延迟及数据规模 |
| 排序／重排 | 相同候选集的相关性或场景标签评测，约束满足与多样性变化 | 特征名称及已加载模型、推理延迟、数据隔离条件 |
| 广告效果预估 | 有标签时的预测与校准评测，标签及观察窗口明确定义 | 样本选择、分桶条件；不替代投放收益验证 |
| 内容加工／索引 | 原文覆盖、定位回读、关系依据、更新删除与检索可见性 | 加工吞吐、更新时效、磁盘／内存、构建峰值 |
| Agent | 任务成功、工具调用、证据支持、引用回读、结果完整性及不足状态 | LLM／工具次数、实际 usage、延迟、失败与取消 |
| 训练闭环 | 可复现的数据切分、基线对比、导出加载和在线消费者生效 | 合成／人工／行为样本量、训练资源与模型适配范围 |

接口／装配测试通过、离线效果改善、生产规模成立是不同结论。验证记录须分别说明；数值对照与效果评测放在测试和离线流程，不插进每次请求的业务路径。

## 写入范围与配套产物

一次任务只补齐所涉及能力的算法实现、数据产物、调用装配、契约配置及必要验证。上面的完成条件不要求新增线上审批、逐层校验或通用工作流。

目录依据为 [项目目录及职责](../SKILL.md#项目目录及职责) 与当前源码；框架使用加载 [go-zero 规范](go-zero.md) 和 [tRPC-Agent-Go 规范](trpc-agent-go.md)。改动目录／import／schema 时执行相应 [边界验证](go-zero.md#按影响执行验证)，不删除测试绕过边界。
